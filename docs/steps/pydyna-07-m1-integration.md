Status (25 Nov 2026): built, uncommitted; waiting for the user's commit OK, the merge of `main` (CR-1 follow-up `6ca00b4`, M2 completed up to `5ba653e`) and the Linux checks. Existing databases are retained; none is rebuilt by this step.

## Implemented

* The PyDyna group owns the `pydyna` config section. `knowledge_root` defaults to `knowledge/pydyna` inside the project. The example is `config/examples/pydyna.yaml`.
* Legacy `database_path`, `keyword_reference_path` and `dpf_core_database_path` keys remain declared for compatibility. Live M1 searches accept them only if they match the root's standard layout; otherwise they return a migration error. Set `knowledge_root` and clear the legacy keys when relocating the databases. The old keyword work helpers still support their earlier path overrides.
* `tools.py` registers four M1 collections, all using `BAAI/bge-small-en-v1.5`, distance `l2`: `lsdyna_keywords`, `pydyna_api`, `pydpf_post` in `vector_db`; `pydpf_core` in `vector_db_dpf_core`.
* The first three declarations are search-only. DPF-Core supplies record and source-file adapters for `champion kb build`. Registering those adapters does not run the builder or modify existing data.
* All four live search tools come from M1's `make_search_tool`, retaining their names. Category values are normalized to lowercase. The PyDyna path filter keeps source, docs and examples plus the old source-less documentation entries; the DPF filters drop tests and repository files.
* Search results now use M1's text format: id, score, distance, source and chunk, then document text. Exact keyword lookups, parameter validation and installed-package API checks keep their existing JSON format.
* M1 owns offline embedding, database access and hash checks. The track's `search.py` (search stub) and `build_index.py` (index builder) are removed (moved to the workspace Trash), as are the old `@function_tool` search tools and backend helpers in `tools.py`. Build DPF-Core with `champion kb build --agent pydyna --collection pydpf_core` (only when the user decides to rebuild).
* Before M1 runs a search, the track wrapper checks the legacy path keys and the keyword category: an unknown category is again an error that lists the known ones (old behaviour). These refusals go through `run_guarded`, so they are audited like every other tool call.
* The `MANIFEST.json` written by the removed `build_index.py` (Linux `vector_db_dpf_core`) has the format M1 reads (test with that exact format).
